# XDK 4432 and Buffy's Default.xbe

What differs from the XDKs the SDK was written against (4831 and later), and how each value was proven. Addresses are
Buffy's. Read the code with `tools/disasm.py <name or address>`, which names addresses from `final.map`.

## The image

- `Default.xbe`, "Buffy: The Vampire Slayer", title ID 0x45410012 (EA-018), North America, built 2002-07-17.
- Libraries, all 1.0.4432: XAPILIB, D3D8, D3DX8, XGRAPHC, DSOUND, XBOXKRNL, WMVDEC, LIBCMT. No LTCG, so library functions
  use their declared calling conventions and the config has no `[abi]`.
- `final.map` on the disc is this build's linker map: timestamp 3D35C92D, 11 seconds before the XBE's header. Its entry
  point 0001:00568EA2 plus `.text` at 0x11000 is the XBE's entry point 0x579EA2, and its section lengths match the XBE's.
- The map's `Rva+Base` column is a PE link address and doesn't match the XBE. An address is the XBE section's VA plus the
  map's offset; `tools/buffymap.py` has the table.

## What the map replaces

`xbe_symbols` finds a title's XDK functions by signature, and has none for 4432. `tools/make_config.py` takes them from
the map instead: an exact API name or an entry of its alias table, nothing looser. It also seeds every function the map
names, and marks the libraries' `*_RD` and `*_RW` parts as data. That took untranslatable instructions from 821 to 0 and
overlapping decodes from 601 to 7.

## Layout

`sdk/xdk/4432/layout.toml` has every key 4831's has, each with the instruction that proves it. Against 4831 the device
fields move in blocks, which is what added struct members look like: 0 up to `IndexBuffer`, 0xC0 for `ZScale` to
`Palettes`, 0x144 for the render targets, then the miniport (at +0x227C here, +0x23C0 there).

## Render states: the numbers differ

`sdk/runtime/gpu/state.h` is edited for 4432. This is the one change that would fail silently: wrong numbers still
compile and run, and read the wrong state.

| Range | 4432 | 5849 |
|---|---|---|
| Simple (reach the host as a hardware method, so unaffected) | 0-82 | 0-91 |
| Deferred | 83-117 | 92-135 |
| Complex | 118-146 | 136-165 |

- The boundaries come from `D3DDevice_SetRenderStateNotInline` (0x591465 and 0x591489).
- Complex states are named one by one by `g_ComplexRenderStateFunctionTable` at 0x59E598.
- Deferred states are 5849's minus 9 up to `PointSizeMax`, from which function touches each index: 83-88 in
  `LazySetSpecFogCombiner` (`EnableFog` touches 83-84, `SetFog` 85-86), 89 in `LazySetTextureState`, 93-95 in
  `LazySetLights`, 96-104 in `GetColorMaterial`, 105-106 in `SetSceneAmbientAndMaterialEmission`, 107-114 in
  `LazySetPointParams`, with 109's dirty flags differing as point sprites do.
- There's no `SampleAlpha` and no `PresentationInterval`. Index 117, the last deferred state, is the swap filter
  (`SwapSetState` compares it with a texture filter state).

Texture stage states match the SDK at every point checked: `ColorOp` 12, `BumpEnvMat00` 22 (where the table's range ends),
`TexCoordIndex` 28, `BorderColor` 29, `ColorKeyColor` 30.

## Library functions the host doesn't replace

`tools/coverage.py` lists what game code calls directly: the host's replacements, with matching argument counts, and these
left to run as recompiled library code.

- **Replaced after reading it:** `D3DDevice_IsBusy` (from `TIF_Render_Implement`'s `Query_IsBusy` and
  `Wait_UntilNotBusy`). It reads the GPU's registers and the push pointer through device fields the host never fills. The
  host's version always answers not busy and logs the first call. A direct call at boot returned 0 with the stack balanced,
  but neither play nor a scripted run has reached it from the game yet. The third caller, `CDevice::KickOff`, is replaced.
- **Not reached, so left alone:** `DirectSound::CMcpxAPU`'s destructor. Its constructor is only called from
  `DirectSoundCreateInternal`, whose two callers (`DirectSoundCreate`, `DirectSoundCreateStream`) the host replaces, so no
  such object exists. `XMountMUA` and `XUnmountMU`: their callers in `HandleMemoryUnitChanges` act on device changes, and
  the host never reports a memory unit, as a console with none inserted wouldn't. `MountMemoryUnit` and `UnMountMemoryUnit`
  call them too and may be reached through a vtable, which hasn't been traced.
- **Fine as they are, checked:** `D3DDevice_SetVertexShaderConstant` (`CD3DMatrixState::UpdateRenderRegisters`, the main
  way constants reach the renderer: about 260,000 calls in 31 s of the first level). It pushes methods 0x1EA4 and 0x0B80
  with the register biased by 0x60, and the host's walk of the push buffer takes them, seen as registers 0, 48 and 64
  loading 96, 144 and 160. Also `IDirectSound_GetTime` (kernel time), `IDirectSound_SetCooperativeLevel` (returns 0),
  `IDirectSoundStream_SetVolume` and `_Pause` (jump to replaced functions), `XGetDevices` and `XGetDeviceChanges` (read
  the record the host fills), `D3DDevice_GetRenderTarget` (reads a field the host mirrors).
- **Expected to be fine, not checked:** resource creation and locking, the `Direct3D_*` queries, `XGSwizzle*`, and the
  WMA and WMV decoders. `D3DDevice_SetRenderState_ZBias` is left native by the SDK itself, as in later XDKs.

The report counts direct calls only, so calls through vtables or function pointers aren't in it. It also doesn't check
the argument conventions of hand-written handlers, such as the CRT math below.

## CRT math

The CRT's math checks its argument in a helper and branches on the flags the helper returns. The recompiler doesn't carry
flags across a call and return, so the SDK computes these on the host. Its `crt_*` handlers replace the body shared by a
function's two entries, not either named entry: x is already in `st0`, and for `pow` x and y sit above the return address
with y in `st0`. Binding one to `_acos` would leave the x87 stack wrong with no error.

The map doesn't name the bodies, so `tools/make_config.py` reads each from the call in its register entry: `__CIacos` calls
0x57F795, `__CIasin` 0x57F951, `__CIsqrt` 0x5800DD, and `__CIpow_default` 0x57EABC. The acos body's offset from its entry,
0x1D, is the same as in Fellowship of the Ring.

`fmod` needs no handler. `__CIfmod` (7 callers, including `MathWrapFloat`) goes through `__cintrindisp2` and `__trandisp2`,
which pick a handler from a jump table by the classes `fxam` gives, and nothing branches on flags across a call. The
recompiled code was called directly with 16 pairs of values and compared with `std::fmod`: the x87 stack and `esp` stayed
balanced and 14 matched. The other two are the CRT's own table: a zero x goes to `__rtzeropop`, so `fmod(-0, 2)` is +0, and
an infinite y goes to `__rtindfpop`, so `fmod(5, inf)` is NaN.

## What the game does at boot

- **Disc check:** `XapiVerifyMediaInDrive` (0x57C9F2) sends the Xbox drive's own authentication. When it fails, `XapiInitProcess`
  skips the drive letters and the game shows its bad disc screen. `src/game/hooks.cpp` passes it.
- **Install:** the game copies `Install.dat`'s files to `Z:` on first boot (about 107 MB, under a second here).
- **Restart:** starting a level calls `XLaunchNewImageA` on the game's own `d:\default.xbe`, then `HalReturnToFirmware(2)`.
  The host restarts its own process with the launch data, so a level starts in a fresh process and a pad script's frame
  numbers start again from there.
- **Bug log:** `TGameManagerImplementation::MapSet` names a file `Bug_<level>.Log` and calls `ReportBug` (0x19F00) with an
  "Initializing" header, which is the `NtCreateFile: no mapping` warning at each level load. `ReportBug` keeps the message in
  an array, then appends it to that file with `fopen(name, "a")` and skips the write when the open fails, so the warning is
  harmless. Other reports from the game would be lost the same way: hook `ReportBug` to see them if a later level misbehaves.

## Widescreen

`src/game/widescreen.cpp`. The game has no widescreen mode of its own: `XGetVideoFlags` is only compared with 0x40.

- **3D:** `View_InternalSetup` (0x2A4870) builds both the projection and the culling planes from the half fields of view, so
  the horizontal one (0x7F4248) is widened during that call and put back after. `View_SetViewport` reads the stored value
  back into `View_SetFOV`, so leaving it widened would widen it again. Only a 640x480 view is widened.
- **2D:** pretransformed draws on the 640x480 back buffer go through `gpu::g_screen_space_hook`, which keeps them in
  proportion in the middle. A draw 90% of the width or more stays as wide as the frame, which is right for fades but
  stretches the pause screen's misty backdrop.
- **4:3:** `app::g_frame_43` holds the frame at 4:3 outside levels and during movies. `MapSet` (0x18800) marks a level: each
  level and the front end is its own process, and the front end's logs have no `MapSet`. The title screen's 3D set shows
  what's built past its frame if widened. Movies are read from what `Movie_Playing` reads (0x7715E0 and 0x7F30E8), as
  `MainThreadProc` is a worker that outlives each movie.
- **Also read from this:** the same pretransformed test is `gpu::g_screen_space_test`, and the movie test sets `gpu::g_movie`.
  The renderer's 2D settings (`smooth_2d`, the HUD's sharpening, `console_textures` leaving 2D alone) and its movie exceptions go by those.
- **Not traced:** `ILightHalo::Render` is the only direct caller of `TGO::WorldToScreen`, and lantern glows sit on their
  lanterns. Anything else that places 2D from a 3D position through a vtable would be pulled towards the middle.

## Menu text

Two things are drawn on the same strings, both the game's choice (`GUI::TBuffyManager::DrawString`, 0x218410):

- **The dark copy behind selected text is a drop shadow.** With the manager's flag at +0x474 set (`TBuffyMenu::OnLoad` and
  `OnUpdate`, `TMenuTitle::OnUpdate`, `IPauseScreen::SetOpen`, `IInventory::RenderModeStrings`), text in any colour but
  the unselected 0x8C5FFF is drawn in opaque black at its place, then in its colour 5 console pixels right and 5 up. Clearing
  the flag removes every dark copy on the Display screen and puts the text back where the shadow was. The shadow under a selected "Off"
  can read as "On", but no "On" is drawn there: the bright "ff" hides the top of the shadow's.
- **Unselected text goes through `TTextureImplementation::Draw2DWavy`** (0x23260), which is a pretransformed line list with
  one horizontal line per console row, shifted by a sine wave. The target's lines are one of its own pixels wide, so at
  1440 lines about two thirds of the rows inside the letters were empty. `gpu::LinesToQuads` draws each line as the
  console pixels it covers. `vk.cpp` calls it; `d3d12.cpp` still draws `LINELIST` and needs the same call.

The hairline on the title screen's moon is painted in its texture (`256x256_ad96e5edd37dd742`): rays from a crater.

The hard horizontal edge across the top of the main menu, 16 console lines down, is painted in the frame's top piece
(`512x128_a39f4adfc98db32c`, DXT4/5, drawn at 0,0 over the moon with source alpha). Its alpha fades smoothly past that line,
but its colour steps at rows 16 and 17: average RGB 5.4 at row 15, 15.1 at row 17, the largest step in the texture. Above
that the colour is nearly black. The top right piece (`128x128_e9bd299408d27071`) has a weaker step on the same line. The
65,536 bytes are on the disc as they are (offset 2014433900 in the ISO) and a separate DXT5 decoder matches `DecodeLevel`
to within rounding. A replacement texture with rows 0 to 16 given row 17's colour and the same alpha removes the edge from
the frame. Not compared with a console picture. At 1440 lines the step covers rows 47 to 52.

The bad disc screen's marks under some letters are a different thing. That text is a quad list that never reaches
`DrawString`, with quads on whole coordinates and texture coordinates half a texel in: a glyph 16 rows high at y 220 to 236
reads v 80.5 to 96.5 of its 256x256 atlas with linear filtering. Upscaled, the bottom of each quad also reads v 95.5 to 96.5,
which runs into the atlas's next row of glyphs. Taking the half texel off in a test left only faint traces of the marks. A
console samples whole y values, so 80.5 to 95.5, every one a texel centre, and shouldn't show them, though that's from the
numbers and not checked on hardware. It's left alone: the screen needs a failed media check (`XapiVerifyMediaInDrive`, always
passed here; forcing it takes 0xC0000001), and removing the half texel changes how 2D is read everywhere.

## Frame rate

The 60 is the game's own: `TGame::EndFrame` (0x86190) spins until 1000 / the limit at `[[this+0x20]+0x7C]` ms have passed
(`fpsLimit`), and a limit of 0 skips that. The host's `Pace` and v-sync come after it. With `app::g_high_frame_rate` the hook
in `src/game/hooks.cpp` sets the limit to 0 and `Pace` holds 120.

`TGameManagerImplementation::Frame` measures the real time since the last frame and passes it to `ScriptUpdate`, and runs
whole 1/60 s ticks from what has built up. Measured at 120 against 60, with the same controller input by the clock:

- A walk of about 2.4 s covered 288.5 units against 292.6, and an A press moved her 35.7 against 35.2. The intro's
  movement ran at 51.2 units/s against 51.0.
- While walking, the player's position changed on 30 frames of every 60, so it steps at 60 a second. During the intro it
  changed on every frame. The camera changed on every frame while walking and turning, and the vertex shader constants of
  the frame always did, so the frames between steps aren't copies.

Not tested at 120: combat, other levels, scripted timing. The console never ran below 1/60 s a frame, so anything in the
game that assumes it could misbehave. A character stepping at 60 under a camera moving at 120 may show as slight judder.

## One processor

The game was written for the Xbox's single CPU, and guest threads here run in parallel. macOS can't bind a thread to a
core, so the SDK's `one_core` setting does nothing on this platform.

- `CLocker` (`Lock` 0x2AA870, `Unlock` 0x2AA950), the engine's own lock, changes its count at +8 with a plain read, add
  and write. During the first level load the `DiskManager` lock's count stuck at -1 and two threads waited until
  `ShellAbort` ("Locker DiskManager waited too long"). Both are replaced with atomic versions in `src/game/hooks.cpp`.
- Other unsynchronised guest code may have the same problem. If more appear, serialising guest threads as
  Fellowship's `fotr_threads.cpp` does is the general answer. Nothing so far calls for it.

A read of the code on 2026-10-31 found no second case. It's a partial audit, not a proof:

- The threads seen in a level are the game's own three, `TDiskManager::ThreadProc` (0x2BB4C0), `MainThreadProc` of
  `D3D_Bink` (0x2975A0) and `MultiThread_Callback` of `winsound` (0x670C0, one for each stream of music), and two from
  `xapilib`, started through 0x579E33 and 0x576EED. Those two weren't read.
- The disk thread's shared state is inside `CLocker`, in the part read (the first 44 of its 70 instructions). The Bink thread
  uses `g_d3dLocker` too, with some flags read outside it; only its first 40 instructions of about 330 were read.
- `CMultiThreadSoundBuffer` keeps a state at +0x40 (1 to 5) with plain reads and writes. The stream's thread moves it forward
  and sleeps 20 ms between steps; the main thread only writes it in `Stop` and `ReleaseSoundBuffer`, from 2 to 3. If the main
  thread stalled between its check and its write while the stream moved on to 4, the state would go backwards. Also, ARM could
  show state 2 before the fields set up ahead of it. Both windows are tiny, and neither has been seen.
- Generated code reads guest memory as plain memory, so the compiler could turn a wait with no call in it into an endless
  loop. Of the game's code, none waits that way on a fixed address: its waits call `Sleep`. The scan found 12 such loops, all
  in XDK code polling hardware (`D3D` `pusher` and `mpintr`/`mpcore`, `DirectSound` `gpdsp` and `mcpbuf`, `xapilib`
  `devsys`), plus one at 0x14688 in no named function. Those would hang on a register, not on another thread. The scan covers
  loops of up to 14 instructions.
- The whole game has two `lock xadd` instructions, so atomics are not how it shares data.

## GPU features the game does and doesn't use

Read from the map and the code, for what the Vulkan renderer needs:

- **Visibility tests:** not used. `D3DDevice_BeginVisibilityTest`, `EndVisibilityTest` and `GetVisibilityTestResult` aren't in
  the map, so the game can't call them. The Vulkan renderer counts no queries.
- **`NOOVERWRITE` locks of surfaces:** not used. `Lock2DSurface` is called only from `D3DSurface_LockRect` and
  `D3DTexture_LockRect`, which pass the caller's flags on, and every call of those in the game passes flags 0. So the late
  read-back path (`SyncLate`) never runs.
- **Point draws:** possible, but not seen. `CD3DIndexBuffer::GetIndexBuffer` turns engine primitive 6 into `D3DPT_POINTLIST`.
  Primitive 6 comes from `Draw_PolyGroup` with a group of type 5 and from `Context_RenderPrimList` with type 0. Which callers
  ask for those wasn't traced. Saved logs from play through the first two zones show no point draw.
- **Point state:** `Mgr_CreateD3DDevice` writes 5.0 to `PointSize` (state 107) directly. Nothing outside the XDK writes the
  other point states (108-114), so there are no point sprites and no scaling by distance. A point is 5 console pixels wide.

The Vulkan renderer draws points at that size times the upscale, and logs `vulkan: a point draw` the first time in each
process, so a playthrough will show whether they ever happen. Direct3D 12 has no point size, so its points stay one pixel.

The render thread (`XBE_RENDER_THREAD=1`) runs with Vulkan but stays off. It has been tried only in a short scripted run into
the first level, not through resizing, full screen or the overlay menu. `vk.cpp` doesn't take the draws the prep thread
assembles (`t_preassembled`, which `d3d12.cpp` does take), so each draw is assembled twice while it's on.

## Hairlines in the level

The thin dashed lines across the first level's surfaces aren't holes, and they aren't a misread of the game's state. Each
dark pixel is written by a triangle the game draws. Measured in one frame of `m00`, with lightmaps alone, at 1920x1440.

The game asks for a depth bias on most of the level: 1,004 of the frame's 1,604 draws. `D3DDevice_SetRenderState_ZBias(n)` is
the XDK's own code and writes a slope scale of `-n * 0.25`, an offset of `-n`, and turns the solid offset on. The state seen at
the draws is -0.25 and -1, so `n` is 1. The renderer multiplies the slope by the upscale, because the slope is per console
pixel. `Mgr_CreateD3DDevice`, `SetRender_StencilState` and `State_InternalSetVar` call that setter; which of them sets 1 for
the level wasn't traced.

A slope bias grows with how steeply a triangle's depth changes across the screen, so a triangle seen edge-on gets a lot of it.
The dark triangles are thin, seen nearly edge-on, and black in their lightmap. They get up to about 1e-3 of bias, against under
1e-5 for most of the level's triangle area (counting parts off screen), and that puts them in front of nearer surfaces:

- **The vertical line:** near-edge-on triangles in several draws, about 0.1 pixel wide on screen and up to 200 pixels long. One
  paints over a wall about 100 units nearer. A dash appears wherever the sliver crosses a pixel center, which is why the
  dashes are evenly spaced.
- **The horizontal seam at `y = -136`:** a flat ledge between an upper and a lower wall. Recoloring only the flat, axis-aligned
  triangles turned these dashes bright, so the first guess of T-junction cracks showing the background was wrong. The bias is
  what mostly lets the ledge show: at one traced pixel it overwrites a wall that's nearer. The two walls also divide the same
  outline differently, leaving a real gap of 0.06-0.2 pixels, but that alone accounts for about what remains with the slope
  bias off (15 of 106 marks).
- **A dotted diagonal near the tree shadows, seen from another camera:** written by a separate 3D mesh (a vertex program, 540
  indices, its geometry not dumped). Removing the slope bias barely changes it (15 marks to 13), so this one has another cause,
  which wasn't found.

| Test, from the same camera | Vertical marks | Seam marks |
| --- | --- | --- |
| As the game asks | 75 | 106 |
| Slope bias off | 1 | 15 |
| Bias capped at 1e-4 | 4 | 103 |
| Bias capped at 3e-5 | 4 | 102 |

The renderer is left doing what the game asks. Nothing here shows a real console differs: it gets the same state and the same
geometry. Drawn here at 480 lines the marks remain: fewer by eye, each three times larger. That is this renderer at the console's
size, not the console's own rasterizer, and no console picture has been compared.

Removing them would mean going against the game's state. A cap would remove the vertical line but not the seam, because the ledge
and the walls are nearly tied: at one traced pixel their depths differ by about 1e-6. A cap would have to come down near the
walls' own bias, and 87% of the triangle area gets more than 3e-6, so it would strip the bias from most of the level. A cap also
needs the `depthBiasClamp` device feature turned on, which the test above didn't do. Turning the slope off clears both, but
changes the bias on every level surface, and whether anything relied on it wasn't checked.

## Achievements

The original game has no achievement system, so the port uses `sdk/runtime/app/achievements.cpp`. It's built on macOS, and Buffy's
list is in `GameInfo::achievements` (see "The set"). It needs nothing outside the game.

At each unlock the game writes the file, then shows its corner note, unless a launcher has taken over by holding a lock
(`LauncherShowsNotes`). The game never creates the lock file, and the kernel drops the lock if the launcher goes away, so with no
launcher the note always shows. The SDK's Mac host also closes the log with `Exit (signal N)` on a crash, which tells one from a
force quit.

`kernel::Relaunch` and `kernel::Shutdown` call `ach::Flush()`, because `ach::Add` saves only every 10 s. `Flush` also passes any
notes still up to the next process in `XBE_ACHIEVEMENT_NOTES`. A level restart replaces the process, so an unlock from finishing
a level would otherwise reach the file but never show. A carried note restarts its six seconds.

Tested with temporary definitions in throwaway folders:
- An unlock at the top of `Relaunch`, on a real restart into a level: the note showed in the next process, over the black loading
  screen, and didn't return after a second restart.
- A counter added about a second before quitting wasn't on disk until the quit wrote it, for both `terminate()` on the app and
  SIGTERM on the bare program. The app's file is `logs/achievements.txt` in its data folder.
- The F10 Achievements page lists earned and unearned entries, with the time earned.

Not covered: a crash or `app::Fail` doesn't flush, so it can lose up to 10 s of counters (unlocks are saved at once). The
`[achievements] notify` setting isn't in the macOS menu's `kLive` list, so it can only be changed in `settings.toml`. These changes
haven't been compiled on Windows.

Buffy's list shouldn't call `SharedDeeds`: its kill names are The Lord of the Rings', and `Fate` and the virtues are the Athelas
launcher's.

### Icons

`tools/make_achievement_icons.py` writes `assets/achievements/<id>.png` from the disc. `build.sh` copies them beside the program,
and `bundle.sh` into `Contents/Resources/achievements`, where the game's note reads them. They are crops at the
source's own pixels, 70 to 220 square, with the corners cut off when drawn.

- **Art:** `interfc/levelThumbnails.mtx` for 23 and `media/launch_buffy.xpr` for the moon and Buffy (`game_hard`, `kills_500`).
- **MULTITEX:** count at 0x14, then a 0x80 byte record per texture with its name at 0x3C and, from 0x7C, width, height, then at
  0x98 format, offset and size. The thumbnails are 55 textures of 256 x 128 DXT5 (format 5), not swizzled, with the picture in about
  the left 170. The file is also in `install.dat`, and the `levelthumbnails` names are in `res_null.pak`.
- **Not used:** the HUD's art (heart, flame, button rings) and the character textures. They came from `[textures] dump`, which needs
  a run, and how they are stored in a `.pak` hasn't been worked out, so a build tool can't reach them.
- **The note:** needs the Vulkan renderer, as `app::g_ui_picture` is null on Direct3D 12. Vulkan on Windows would draw an icon, but
  no Windows build copies them yet, so there it logs one `no picture` line for each achievement earned and shows text alone. The
  upload is recorded between `ImGui::NewFrame` and the menu's rendering. The menu's page is still text. Tested with a probe build whose screenshot ran after
  the menu drew: the note with its icon, and the plain note with no icon files. Not compiled on Windows.

### The set

The 25 achievements are listed in `src/common/game_info.cpp` and earned in `src/game/achievements.cpp`. The rules: cheats don't
disqualify, existing saves earn nothing, and only kills credited to Buffy count.

`IMapCompleted::DoMapChange` goes on along the level table: from `M12_Apse`, the next process opened `m12_bronze-ending` (only this
one was checked to the next level's load). `IMapIndexer::DoMapChange` goes to the map's name with its last
digits replaced by `[this+0x290]`, which can be backwards: `M07_Docks_5` has one exit to `M07_Docks_4` and one to `M07_Docks_6`. So a
level's achievement needs `IMapCompleted`, or `IMapIndexer` with the next level in the table as its target.

| How it was tested | Achievements |
| --- | --- |
| Scripted play on the real hook | `kills_1`, `die_once`, `game_finished`, `game_hard` (and not on Normal), `history` |
| The game's own exit code, called by a test driver (`IMapTrigger::Trigger`) | `boss_malik`, `boss_urd` (the backward exit earned nothing), `boss_master`, `chapter_deathless` |
| The game's own `ISecretCounter::Trigger`, called by a test driver | `secret_1`, with the per-level and total counters; `GetCount` read 1 of 1 |
| Same code path as above, with a threshold or table row not reached | `kills_100`, `kills_250`, `kills_500`, `secret_level`, `secret_30`, `secret_all`, `ch_training` and the other 8 bosses |

None of it has come from a real playthrough, so walking into an exit or a secret and actually beating a boss haven't been seen yet.
Only 3 boss levels' exits have been looked at, and the driver skipped the fights, so it doesn't show an exit stays shut until the
boss is beaten. `kills_500` rests on a rough estimate. A note appears over the black loading screen when it's earned at a level's end.

| Any character dies | `ICharacter::Event_Die` | 0x12C740 | About 1.2 s after the above for enemies, 4 s for Buffy |
| Buffy dies | `ICharacterBtvS::DieAsPlayer`, then `TGO::PlayerDeathReload` | 0x206010, 0x939C0 | Cemetery and `M12_Apse` |
| The game's end | `TGBuffyInterface::ActivateEndCredits`, then `IPauseScreen::DoEndCredits` | 0x23EF50, 0x231240 | `M12_Bronze-Ending`, from `IMapCompleted::DoMapChange` |
| Difficulty | `TScriptFunction_General::DifficultyLevel` | 0x15AB40 | Returned 2 on a game started on Normal. It returns `TGO::Interface_Options` +0x1C |

Difficulty: only `TMenuDifficulty` (which writes 1, 2 or 3 and a value in `OnLoad`) and `TMenuLoadSession` write that field, so the
pause menu can't change it mid-game. A "finish on Hard" check can read the field directly when the credits start. Normal = 2 and
Hard = 3 were seen, the second through `game_hard` being earned on Hard and not on Normal. Easy = 1 is inferred.

Traps:
- `TGameMapManager::Queue_MapChange` (0x8BBD0) also fires for a death reload, the first level and Extras' Buffy History 101
  (`G00_BuffyHistory`), so it doesn't mean a level was finished.
- `IMapCompleted::DoMapChange` (0xEEB50) has three branches: end credits (`[this+0x290]`), `TGCoreInterface`'s vtable +0x6C when
  `ILevelProperties` +0xC4 is set, and `TGO::Map_QueueChange` (0x95360) with the current map and index `[this+0x28C]`. In
  `TGBuffyInterface`, +0x6C is `ActivateArenaMenu`, a do-nothing stub. Only the credits branch has been seen. The map names
  suggest the last branch moves between parts of a mission, so finishing a part may not mean finishing a mission.
- `IMapIndexer::DoMapChange` (0xEECD0) and `ICharacterBtvS::Event_MapCompleted` (0x2058D0) fire at the end of Buffy History 101, so
  a level-finish hook on either has to exclude `G00_BuffyHistory`. History fired no kill or end-credits hooks. Neither hook fired
  in `M12_Bronze-Ending`.
- Credits from Extras fires none of these hooks, so `ActivateEndCredits` can't be earned from that menu.
- `IJournal::HandlePickup` (0x1F6FC0) fires at each level start with Buffy's items (crossbow, arrows and others). Pick-ups during
  a level weren't tried, so it may also see those, but a hook would have to skip the level start.
- `IMaster::Init` (0x20C810) fires twice in `M12_Apse` and once in `G00_BuffyHistory`, so it doesn't mean a boss fight started.

Not seen firing: `ISecretCounter::Trigger` (0x23C7A0) and `FoundAllLevelSecrets` (0x23C6D0), the pause menu shows a per-level
"Secrets Found: 0/1"; `IMapCompleted` going to a next map; `IMapIndexer` or `Event_MapCompleted` in a story level; any boss's
death. A scripted Buffy dies in the Apse about 28 s in, without killing the Master.

### Enemy counts

A rough sample of characters created at level load (`ICharacter::Init`), leaving out Buffy, `IGenericNpc`, `IRaverGirl_Human` and
`ISpike`: `M01_Highschool_1` 15, `M03_Cemetery_2` 24, `M07_Docks_1` 26, `M09_Foundry_1` 15. That assumes the classes counted are all
hostile. Enemies scripts spawn during play aren't included, and boss levels hold far fewer. At about 20 for each of roughly 35 regular
levels, a full run has somewhere around 700 enemies, not all of them credited to Buffy (5 of 8 deaths in two scripted Cemetery runs).

### Bosses

The names and order are from UnSub's fighting guide (2003). The levels come from the level table's objectives and from logging the
character classes that spawn when each level loads, using `ICharacter::Init` (0x12FBB0). A class being in a level doesn't prove a
fight there: `IDelusioner` and `IDemolisher` are also in `M07_Docks_6`, `M10_Sunken-church_3` and `M12_Apse`, and `IRhakshasa` in
several levels. No boss has been fought in a test.

Several of these don't die in a way a death hook would see: the guide says Spike can't be dusted and Angel ends in a cutscene.
Leaving the boss's level is the one signal they all share, so that's what achievements should use.

Cheats and arenas: `TScriptFunction_General::CheatActivated` (0x15AB00) tests a bit of the mask at `TScriptRunOptions` +0x34. No run
called it. Direct readers of the mask:

| Bit | Read in | Meaning |
| --- | --- | --- |
| 0x01 | `TManager_Buffy::Frame_Tick` | Set by `TMenuCredits::OnMessage` before it loads an arena |
| 0x02 | `ISlayer::Power_Change` | Not read further |
| 0x04 | `IGenericNpc::Init` | Not read further |
| 0x08 | `TMenuCredits::OnMessage` | Adds `d` to the arena's name, so `res_arena01d` and so on |
| 0x10 | `ICharacter::Reaction_Handle` | Not read further |

`TMenuCredits::OnMessage` has hidden controls that load `Arena01` to `04` when active. How a player makes them active wasn't traced
(`[this+0x48]` gates the whole handler), and Credits on a new save showed only the scrolling names. The only write to the mask found
is that bit 0x01, from a scan of the instructions just after each `Interface_RunOptions` call, which would miss a write through a
saved pointer. `cheats` and `cheatarenas` look like console variables, registered in `TGameManagerImplementation`'s constructor;
whether they feed the mask wasn't traced. No way for a player to set 0x02, 0x04 or 0x10 has been found.

Extras on a new save has Buffy History 101 and Credits. Whether finishing the game adds to it isn't known.

Saves: each `.ses` is 131,748 bytes. As text they show only map names: `M00_SpanishMission_1` in three of the four saves looked at,
with `M00_SpanishMission_2` as well in the fourth. Nothing else in them has been decoded, so at most "reached this level" could
be credited from a save.

The level table is plain text on the disc (at byte 0x781CB418 of the image), with lines of `EXEC <spawn> <mesh> "<mission>"
"<objectives>" <map> "<parameters>"`. It lists 55 story levels in play order, split into chapters by `HUB01` to `HUB07` (the Library
"Gang Meeting" levels), and declares 77 secrets through `secretcount:`. The pause menu's "Secrets Found: n/m" comes from
`ISecretCounter::GetCount` (0x23C640): m is `TScriptRunOptions` +0x28 and n sums +0x274 of the level's `ISecretCounter`s.
`Trigger` counts each activator once. `M00_SpanishMission_1` showed 0/1, matching its `secretcount:1`, so the table's total is taken
as the game's. `M11_DreamRealm` runs 3, 1, 4. `SPECIAL` lines list the arenas and `G00_BuffyHistory`.

Levels on the disc, from the `pak` folder: `m00_spanishmission` 1-3, `m01_highschool` 1-4, `m02_bronze` 0-4, `m03_cemetery` 1-4,
`m04_mausoleum` 1-2, `m05_sunken` 1-4, `m06_mansion` 1-2, `m07_docks` 1-6, `m08_highschool` 1-4, `m09_foundry` 1-5,
`m10_sunken-church` 0-3, `m11_dreamrealm` 1, 3, 4, `m12_apse`, `m12_bronze-ending`, plus `g00_buffyhistory`, `hub01` to `07` and
`arena01` to `04` (each with a `d` version).

## Not yet proven

Frames from the software reference renderer are the only drawing evidence so far, and it isn't the renderer players will
use. Other host assumptions may hold 5849's values without a named constant, such as the D3D resource header bits or the
pixel shader definition's field offsets. In the first level most of the ground is black and there's a black strip down
the left of the screen, which may be one of these or the reference renderer itself; that's not diagnosed.
